The public C API

This page documents mex/rsApi.h, a small stable header that a user's own MEX file or standalone C program can link against to evaluate the ITRS ↔ GCRS rotation with no MATLAB in the loop.

Why it exists, in one measurement. MATLAB's own call overhead is about 5–15 µs and cannot be optimised away — it is the MEX round trip, the arguments block and the struct assembly, not the arithmetic. An orbit integrator evaluating its right-hand side a hundred thousand times per arc pays that overhead a hundred thousand times. rsApiRotation is measured at 0.564 µs per call by test/c/testApi.c on the reference host. The accuracy is identical; only the overhead differs. If your integrator needs better than about 15 µs per evaluation, it has to live in C.

Measured, 2026-08-04, and it changes the advice. On the reference host a single-epoch rotationItrsToGcrs call costs 491 µs on the exact path and 469 µs with an interpolant — a speedup of 0.99. At N = 1 the cost is MATLAB-side overhead, which the interpolant cannot touch, so the interpolated mode buys nothing for single calls and P19's "< 15 µs per single-epoch call" target was inconsistent with the same prompt's statement that 5–15 µs of overhead cannot be optimised away. The interpolant is for arcs, where per-epoch series evaluation dominates. For a hot loop, use this C API — 0.564 µs per call, measured — and not the MATLAB interpolated path.

The workflow

MATLAB builds the interpolant and writes it; C reads it and evaluates it. The two halves never run at the same time.

% MATLAB, once per arc
eop  = referenceSystem.readEop("data/eopc04_20.1962-now");
span = referenceSystem.daySecondToEpoch([57754 0; 57755 0], "UTC");
eoi  = referenceSystem.earthOrientationInterpolant(span, 'Eop', eop);
referenceSystem.writeInterpolant(eoi, "arc.eopi");

The struct eoi carries its validity interval, node spacing, fit degree and the measured maximum residual against the exact model, so the accuracy of the fast path is reported at run time rather than assumed.

The interpolant file

writeInterpolant emits a plain-text file that rsApiReadInterpolant reads. It exists in two formats and both are read:

FormatChannels per panelWritten by
16 — X, Y, s, xp, yp, ΔUT1 up to v2.1.178
27 — the same, plus the excess length of day v2.1.179 to v2.1.238
26 — as format 1, with method and zonalTides provenance lines v2.1.239 onward

The rotation reads the six channels X, Y, s, xp, yp and ΔUT1. A seventh channel in an older file is read over and not used. The header is read by key and value, not by line, so a year of one-day panels, whose taiMinusUtc line runs past a thousand characters, reads whole; keys the reader does not know are skipped.

The channel count is read from the file's own quantity line, never inferred from the version number. A reader that trusted the version would stride correctly only for as long as the two never disagreed, and would then be wrong in a way that produces smooth, plausible coefficients. The version guards one thing: an unknown format is refused rather than read hopefully.

The C reader has read format 2 only since v2.1.221; MATLAB's readInterpolant always did. Until then rsApiReadInterpolant admitted format 2 at the version line and refused it at its final check, so every file writeInterpolant had written since v2.1.179 came back RS_API_BAD_FILE. The C suite read only a format-1 file, which is why nothing noticed; it now reads one of each.

If you fill in an rsApiInterpolant yourself — as the worked propagator below does — set the new quantityCount field. Zero means six, so code written before v2.1.179 keeps its meaning and needs no edit; new code should say what it means. Any other count than 0, 6 or 7 is RS_API_BAD_INTERPOLANT. This default is not a courtesy: adding the field without it silently changed the meaning of every hand-built interpolant, made the panel term in the coefficient offset vanish so that every panel read panel 0, and moved the residual against the direct chain from 1.16e-16 to 6.53e-07 — small enough to read as a tolerance and entirely wrong. The standalone C suite caught it; nothing else would have.

Ownership

This library never allocates. The caller owns every buffer, which is why rsApiReadInterpolant uses a two-call protocol: call it once with both buffers NULL to have the header parsed and the sizes filled in, size your arrays with rsApiInterpolantSize, then call it again to fill them. The alternative — the library mallocs and the caller remembers to free — is the arrangement that leaks in an integrator reloading panels once a day for a month.

On any status other than RS_API_OK the output is untouched, and a failed read leaves the interpolant unusable rather than half filled: its coefficient pointer is set to NULL, so a caller that ignores the return value gets RS_API_NULL_ARGUMENT from the next call instead of a rotation built out of whatever happened to be in the buffer.

Thread safety (risk R11)

rsApiRotation, rsApiRotationRate and their day-and-second forms take the interpolant as const and hold no state between calls, so any number of threads may share one interpolant concurrently. rsApiReadInterpolant writes into it and is not thread safe; it must complete before the threads start.

The rate is differenced, not differentiated

rsApiRotationRate takes a central-difference step in seconds. That is the same construction the direct MATLAB path uses under decision D28, so the two agree. Differentiating the Chebyshev panels analytically would be faster and is a reasonable thing to want — it is a separate prompt, not a variation to be slipped in here, because the two would then disagree at a level nobody had measured.

The rate is the derivative of the rotation. The Earth rotation angle is differentiated in closed form, and its rate is formed from the ΔUT1 panels at the same three samples:

omega    = eraSlope * (1 + d(UT1 - TAI)/dt)
omegadot = eraSlope * d2(UT1 - TAI)/dt2

with each sample's UT1−TAI taken as its ΔUT1 less the TAI−UTC of its own panel, so a shoulder across a leap second sees no step. eraSlope is rsEarthRotationAngleRate(), the ERA slope derived from SOFA's iauEra00 (decision D63). The construction lives once, in rsCore, and rotationItrsToGcrs reaches the same code, so the C and MATLAB rates agree bit for bit on the committed fixtures.

Leap seconds, and what an MJD can resolve

An interpolant may span a leap second since v2.1.226. A panel carries one TAI−UTC, so a leap second falls on a panel boundary, and the file's taiMinusUtc changes there. rsApiRotationRate takes its difference shoulders step SI seconds either side, so a shoulder beyond the boundary is taken at the UTC label that instant has, not at the label plus step. Until v2.1.226 it was taken one second off, and within one step of 2017-01-01 the rate missed MATLAB's by 1.1e-14 1/s. A shoulder that lands inside the leap second itself returns RS_API_OUT_OF_RANGE: 23:59:60 has no MJD. The window is one second wide at +step and at −step. MATLAB's interpolated path refuses the same instants.

An MJD passed as one double resolves about 0.63 µs at current dates (one unit in the last place of 5.8e4 days). The nearest double can lie half of that from the instant meant, and the Earth turns 7.3e-5 rad/s, so rsApiRotation can be up to 2.3e-11 out — 4.6 times P19c's 5e-12 on a direction cosine. Measured against MATLAB at seconds an MJD cannot name: 2.15e-11 on R and 1.57e-15 1/s on Rdot, eleven times D28's 1 nm/s at 7000 km.

In the last 0.3 µs before a leap second the MJD form is out by a whole second of rotation, 7.2e-5 rad: the nearest double there is 0h of the next day, which is one SI second later.

Since v2.1.236, pass a day and a second instead. rsApiRotationDaySecond and rsApiRotationRateDaySecond take the UTC day as a whole-number MJD and the second of that day. UT1 is formed from the second itself, and the panels are read at the same day + sec/86400 MATLAB reads them at. In 0.63 µs the fastest fitted angle, X under precession, moves 1.9e-18 rad, so only the Earth rotation angle needed the second. For the same day and second the matrices are rotationItrsToGcrs's, bit for bit on the committed fixture, including an epoch 0.2 µs before 23:59:60.

A second outside [0, 86400) is carried into the neighbouring days as daySecondToEpoch carries it, with the day before a leap second 86401 s long, and the difference shoulders are carried the same way. The leap second itself — an epoch or a shoulder in it — returns RS_API_OUT_OF_RANGE, as it does for the MJD form. A day that is not a whole number, or a day or second that is not finite, returns RS_API_BAD_EPOCH.

MATLAB itself was out by a second there until v2.1.235. interpolateEop read TAI−UTC at day + sec/86400, which lands 23:59:60 and the last 0.3 µs before it on the next day. Both MATLAB paths then turned the Earth a second ahead, 15 arcseconds, and agreed with each other. The C fixture is MATLAB's result after that fix.

Worked example

doc/examples/exampleRk4Propagator.c is a complete fourth-order Runge–Kutta propagator that links this API. Its force model is a point mass plus J2 — the smallest model that makes the rotation matter, since J2 is expressed in the Earth-fixed frame while the state is integrated in the inertial one, so every right-hand-side evaluation needs one rotation.

cc -O2 -std=c99 -Imex -Imex/sofa -Imex/iers \
   doc/examples/exampleRk4Propagator.c mex/rsApi.c mex/rsCore.c \
   mex/rsCheb.c mex/sofa/*.c mex/iers/*.c -lm -o rk4
./rk4 arc.eopi

It is not a precise orbit determination force model: no third bodies, no tides, no drag, no radiation pressure, no relativistic correction. It exists to show the calling sequence, the ownership rules and the cost, and it should not be mistaken for anything more.
